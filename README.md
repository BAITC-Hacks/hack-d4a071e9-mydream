# Money Graph · HackAlem AI, трек 02 «Финансы»

Локальный MVP для AML аналитика: из транзакционной сети строит объяснимые гипотезы о роли каждого узла, группы связанных участников и очередь проверки. Для анализа нужны три parquet файла организаторов. В этой рабочей папке они уже размещены в `track02/data/`; анализ выполняется локально.

## Исходные данные

Для отдельной проверки ролей на небольшом вымышленном графе используйте [синтетический набор](track02/fixtures/README.md). Он не заменяет данные организаторов.

Архив `track02/materials/data.zip` включён в проект и получен из [материалов организаторов](https://drive.google.com/file/d/1yHdWaSb6gwPAUrqco-KrwR2U_YhzFQFT/view?usp=sharing). Распакуйте его из корня проекта командой ниже. Получатся `track02/data/nodes.parquet`, `edges.parquet` и `transactions.parquet`. Извлечённые parquet не дублируются в GitHub. Схема и параметры выборки описаны в `track02/materials/dataset-README.md`.

## Быстрый старт

Однократная подготовка из корня проекта:

```powershell
Expand-Archive -LiteralPath track02/materials/data.zip -DestinationPath track02 -Force
py -3 -m venv track02/.venv
track02/.venv/Scripts/python.exe -m pip install -r track02/requirements.txt
```

Каждый последующий запуск — одна команда:

```powershell
node server.mjs
```

Откройте <http://127.0.0.1:4173>. В интерфейсе нажмите **Пересчитать модель** для воспроизводимого расчёта из исходных parquet. При повторном запуске доступны ранее рассчитанные результаты. Если на Windows команда `py` недоступна, используйте установленный Python 3.11+ вместо `py -3`.

Отдельный запуск расчёта:

```powershell
track02/.venv/Scripts/python.exe track02/pipeline.py --data track02/data --out track02/out
```

Проверка:

```powershell
node --test
track02/.venv/Scripts/python.exe tests/pipeline_analysis_test.py
track02/.venv/Scripts/python.exe tests/synthetic_data_test.py
```

## Основной сценарий

1. Аналитик загружает локальный граф переводов и видит сводку и ранжированный список узлов.
2. Находит любой `gid` поиском или выбирает узел на направленном графе.
3. Изучает роль, приоритет, вклад каждого фактора в индекс в процентных пунктах, соседей и ограничения наблюдения.
4. Открывает отдельный план дополнительных данных для выбранного gid, переходит к кластерам и выгружает три CSV для дальнейшей проверки.

Алгоритм не утверждает виновность клиента. Роли и приоритеты являются проверяемыми гипотезами, рассчитанными из предоставленной сети переводов. Особенно осторожно следует читать узлы на четвёртом колене: отсутствие исходящих переводов в обрезанном графе не доказывает, что это конечный получатель.

## Вход и выход

Входные файлы: `track02/data/nodes.parquet`, `edges.parquet`, `transactions.parquet`. Архивы и README организаторов сохранены в `track02/materials/`, пример кода — в `track02/starter/`. После распаковки parquet конвейер не читает архив повторно.

Результаты в `track02/out/`; проверенные CSV этого запуска также сохранены в `deliverables/` для сдачи:

- `nodes_roles.csv`: `gid,role,role_score,cluster_id,priority_score,evidence` и наблюдаемые метрики;
- `clusters.csv`: `cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis`;
- `top_nodes.csv`: `rank,gid,role,priority_score,why`;
- `network.json`: данные для локального интерфейса; 18-значные `gid` здесь сохранены как строки без округления.

Сервис предоставляет `GET /api/health`, `GET /api/network`, `POST /api/rebuild`, `GET /api/export/{имя CSV}`. Он слушает только `127.0.0.1`. Ключи, облако и внешние запросы для анализа не нужны.

## Проверяемый метод

На предоставленном наборе проверенный запуск обработал 2 248 узлов, 3 119 рёбер и 4 840 транзакций, выдал 66 кластеров и топ 50 за 1,00 секунды на локальном компьютере. Результат зависит от машины и версии пакетов.

Конвейер считает направленные степени, суммы и число транзакций, активные дни и выборочную посредническую центральность. Упорядоченные правила дают одну из шести ролевых гипотез. PageRank также доступен в выгрузке как вспомогательная метрика, но не влияет на приоритет. Louvain группирует узлы по ненаправленной проекции с логарифмом суммы; направление сохраняется в ролях и графе интерфейса.

Правила применяются сверху вниз; первое совпадение определяет роль:

| Роль | Наблюдаемое условие |
| --- | --- |
| Периферия на границе | Глубина 4 и нет наблюдаемого выхода; продолжение цепочки неизвестно. |
| Периферия без связей | Нет наблюдаемых входящих и исходящих связей. |
| Конечный получатель | Есть входящие, нет выхода в пределах наблюдаемого обхода. |
| Координация | Не менее 2 входов и 2 выходов; посредничество выше нуля и не ниже 90-го процентиля среди узлов с такими связями. |
| Консолидация | Не менее 3 входов и 1 выхода; число входящих связей минимум в 1,5 раза выше исходящих. |
| Распределение | Не менее 3 выходов; узел seed либо исходящих связей минимум в 1,5 раза больше входящих. |
| Транзит | Есть вход и выход, узел не seed, отношение исходящей и входящей сумм от 0,5 до 2 включительно. |
| Прочая периферия | Ни одно предыдущее правило не выполнено. |

Приоритет — взвешенная сумма измеримых признаков: сила совпадения с ролью 30%, процентиль наблюдаемого оборота 25%, процентиль числа связей 20%, процентиль посредничества 15%, средний процентиль числа операций и активных дней 10%. Затем сумма умножается на коэффициент качества наблюдения: ×0,9 для seed, ×0,55 на границе глубины 4, ×0,75 при единственной операции, 0,2 для изолированного узла. В карточке узла показан вклад каждого параметра и вычет за неполноту данных в процентных пунктах. Порогов «виновен/невиновен» нет.

`role_score` означает силу совпадения с правилом, а `priority_score` — очередность проверки. Ни одно из этих чисел не является вероятностью мошенничества. В `evidence` для каждого узла указаны правило и фактические значения; `why` в топе содержит то же объяснение.

## Границы интерпретации

Наблюдаются только исходящие цепочки до четырёх колен; входящие переводы для стартовых клиентов неполны. В данных нет размеченных истинных ролей, сведений о личности клиента или внешних источников обогащения. Поэтому значения score помогают определить порядок ручной проверки, но не служат автоматическим AML решением.

При росте до ~1 млн узлов полную сетевую центральность NetworkX надо заменить приближённым расчётом на ограниченной выборке путей или специализированным графовым движком. Parquet агрегаты и признаки следует считать потоково по разделам графа, кластеризацию запускать на агрегированной проекции, а интерфейсу выдавать только страницу топа и соседство выбранного узла. Проверка входных сумм и ограничения наблюдения должны сохраняться.
