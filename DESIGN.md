## 1. Требования

### 1.2 Нефункциональные

- Время полного прогона ≤ 5 мин (реально: секунды).
- Локально, обычный ноутбук, без GPU/облака. Интернет — только для опционального LLM.
- Детерминизм: одинаковые CSV при повторном запуске (seed у Louvain, стабильная сортировка).
- Формулировки — «признаки консолидации», «кандидат на проверку»; никаких утверждений о виновности.

### 1.3 Ограничения

- Нельзя: хардкод gid, «чёрный ящик», внешнее обогащение, персональные данные.
- 5 часов → каждый модуль должен быть сдаваемым в любой момент после часа 2:30.

## 2. Высокоуровневая архитектура

```
 data/*.parquet
      │
      ▼
 ┌────────────┐   ┌─────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
 │ 1. load    │──▶│ 2. features │──▶│ 3. roles   │──▶│ 4. clusters│──▶│ 5. priority│
 │ + validate │   │ graph+time  │   │ rules+score│   │ Louvain    │   │ + top-list │
 └────────────┘   └─────────────┘   └────────────┘   └────────────┘   └─────┬──────┘
                                                                            │
                          ┌────────────────────────────────────────────────┤
                          ▼                                                ▼
                  ┌──────────────┐                                ┌────────────────┐
                  │ 6. export    │  nodes_roles.csv               │ 7. app (UI)    │
                  │ 3 CSV +      │  clusters.csv                  │ Streamlit+pyvis│
                  │ features.pq  │  top_nodes.csv                 │ поиск gid,     │
                  └──────────────┘                                │ карточка узла  │
                                                                  └────────────────┘
                                                                          │ (опц.)
                                                                  ┌───────▼────────┐
                                                                  │ 8. assistant   │
                                                                  │ LLM по фактам  │
                                                                  └────────────────┘
```

Принципы:

- **Один вход, один выход.** Пайплайн — чистая функция `data/ → output/`. UI и ассистент читают только `output/`, ничего не пересчитывают. Так демо не зависит от пересчёта, а CSV не зависят от UI.
- **Правила, а не модель.** Каждая роль — явное правило с порогом (must-have 3). ML допустим только как дополнительный сигнал аномалий, не как источник роли.
- **Evidence строится из тех же чисел, что и правило.** Функция `explain(gid)` формирует и `evidence`, и текст для демо — одна реализация.
- **Все метрики считаются один раз** и сохраняются в `output/features.parquet`; UI и `explain` берут их оттуда.

### 3.2 Схема данных: `features` (одна строка на gid)

| Колонка | Источник | Смысл |
|---|---|---|
| `gid, depth, is_seed` | nodes | как есть |
| `in_deg, out_deg, in_kzt, out_kzt, in_tx, out_tx` | edges | starter |
| `pass_through` | edges | out_kzt / in_kzt; **NaN** если in_kzt = 0 |
| `truncated` | nodes+edges | depth = 4 и out_deg = 0 |
| `n_seed_src` | edges | от скольких seed получает напрямую |
| `seed_kzt_share` | edges | доля входящих, пришедших от seed |
| `pagerank_w` | graph | PageRank по sum_kzt |
| `betweenness` | graph | невзвешенная, нормированная |
| `hub, authority` | graph | HITS: источники vs сборщики |
| `component_id, component_size` | graph | слабосвязная компонента |
| `in_first, in_last, out_first, out_last` | tx | даты первого/последнего прихода/ухода |
| `lag_days` | tx | out_first − in_first; отрицательный = есть внешний источник |
| `fast_pass_share` | tx | доля исходящей суммы, ушедшей ≤ 2 дней после прихода |
| `active_days` | tx | число дней с транзакциями |
| `max_single_src_share` | edges | доля крупнейшего плательщика во входящих |
| `avg_in_tx, avg_out_tx` | edges | средний чек |
| `same_day_burst` | tx | макс. число переводов одной паре за день |
| `in_cycle` | graph | участвует в цикле ≤ 5 (опц.) |

### 3.3 Правила ролей (`roles.py`), порядок применения — сверху вниз, первое совпадение

Пороги — в `config.py`, здесь значения по умолчанию, подобранные по разведке.

| Приоритет | Роль | Правило (не seed, если не сказано иное) | Ожидаемо узлов |
|---|---|---|---|
| 1 | **coordinator** | `in_deg ≥ 3` и `out_deg ≥ 3` и `betweenness` в топ-2 % и связан с ≥ 2 кластерами | ~10–20 |
| 2 | **consolidator** | `in_deg ≥ 4` и (`pass_through < 0.3` или `out_deg = 0`) — **или** `n_seed_src ≥ 2` и `pass_through < 0.5` | ~40–60 |
| 3 | **distributor** | `out_deg ≥ 10` и `out_deg ≥ 3·in_deg`. Для seed — тоже (seed-распределитель важен) | ~50–60 |
| 4 | **transit** | `in_deg ≥ 1`, `out_deg ≥ 1`, `0.7 ≤ pass_through ≤ 1.3`, `lag_days ≥ 0`, `fast_pass_share ≥ 0.5` | ~30–40 |
| 5 | **terminal** | `out_deg = 0`, `depth < 4`, (`in_kzt ≥ 500 000` или `in_deg ≥ 2`) | ~150–180 |
| 6 | **peripheral** | всё остальное; подтипы в evidence: `truncated` (444), `no_edges` (19), `low_activity` | остальное |

Особые правила:
- **Seed**: `pass_through` не используется (входящие занижены). Seed получает роль только по исходящим (`distributor`) или `peripheral` с evidence «seed; входящие вне выборки».
- **`truncated`** → всегда peripheral с evidence «обход остановлен на 4-м колене; получил X от N; исходящие неизвестны». Реализовано: `terminal_likeness` — среднее процентилей in_kzt и in_deg среди подтверждённых стоков (не seed, depth 1–3, out_deg = 0), и `truncated_candidate` — проходит пороги terminal; 33 из 444. Скор, не роль; в evidence рекомендация «запросить 5-е колено».
- **role_score** = превышение порога, нормированное 0–1: `min(1, (metric − threshold) / threshold)` по основной метрике правила; для peripheral — 0.2 фикс.

Шаблоны evidence (≤ 200 символов, только числа из features):

```
consolidator: "получает от {in_deg} плательщиков ({in_kzt:,.0f} KZT, {n_seed_src} seed), отдаёт дальше {pass_through:.0%}"
transit:      "получил {in_kzt:,.0f}, отправил {out_kzt:,.0f} ({pass_through:.0%}); {fast_pass_share:.0%} ушло ≤2 дней"
distributor:  "рассылает {out_deg} получателям на {out_kzt:,.0f} KZT, средний перевод {avg_out_tx:,.0f}; получает от {in_deg}"
terminal:     "получил {in_kzt:,.0f} от {in_deg} плательщиков, исходящих нет; колено {depth} (не обрезан)"
coordinator:  "связывает кластеры {clusters}; посредничество топ-{bt_rank}; in {in_deg} / out {out_deg}"
peripheral:   "1 входящий перевод на {in_kzt:,.0f}; ниже порогов" | "обрезан 4-м коленом: ..." | "seed без переводов в выборке"
```

### 3.4 Кластеры (`clusters.py`)

- `louvain_communities(G.to_undirected(), weight="sum_kzt", seed=42, resolution=1.0)` — в README оговорить, что кластеризация на ненаправленной проекции.
- Маленькие компоненты (< 5 узлов) — отдельные кластеры без дробления.
- Для каждого кластера: `n_nodes, n_seed, sum_kzt_internal, top_gids` (топ-5 по priority), `hypothesis` — шаблон по составу ролей:
  - есть consolidator и ≥ 2 seed → «сбор средств с курьеров в точку консолидации {gid}»
  - есть distributor и мало seed → «веерное распределение от {gid}»
  - только transit/peripheral → «транзитная цепочка, точка назначения вне выборки»
  - < 5 узлов → «изолированный фрагмент, недостаточно данных»
- Опционально LLM переписывает гипотезу человеческим языком **из тех же фактов**.

### 3.5 Приоритет (`priority.py`)

```
priority_raw = 0.30·rank(in_kzt) + 0.20·rank(in_deg) + 0.15·rank(betweenness)
             + 0.15·n_seed_src_norm + 0.10·rank(pagerank_w) + 0.10·role_weight
role_weight: coordinator 1.0, consolidator 0.9, distributor 0.6, transit 0.5, terminal 0.4, peripheral 0.0
штраф: truncated → ×0.3; seed → ×0.5 (уже известны следствию)
priority_score = minmax(priority_raw) ∈ [0,1]
```
`rank(·)` — процентильный ранг, чтобы выбросы не давили. `top_nodes.csv` — топ-30 по priority, `why` = evidence + «приоритет за: {два главных вклада}».

### 3.6 CLI и API (`cli.py`)

```
python -m moneygraph run   --data data --out output      # весь пайплайн, печатает сводку по ролям
python -m moneygraph explain <gid> [--out output]        # объяснение роли за минуту (M3)
python -m moneygraph check --out output                  # проверка схемы CSV (M2, M4, M5)
```

### 3.7 UI (`app/streamlit_app.py`)

Читает только `output/`. Три панели:
1. **Поиск gid** → карточка: роль, role_score, priority, evidence, кластер, список входящих/исходящих с суммами; кнопка «объяснить» = `explain(gid)`.
2. **Схема сети**: pyvis, окрестность выбранного gid на 2 колена (по умолчанию — топ-кластер), стрелки = направление, толщина = сумма, цвет = роль, форма = seed. **Не рисовать все 2 248 узлов** — тормозит.
3. **Топ-лист и кластеры**: таблицы из CSV с фильтрами по роли/кластеру.

### 3.8 Ассистент (`moneygraph/assistant.py`, сделан)

Вопрос → парсер gid из текста → подграф из features/edges → LLM формирует ответ **только** из переданной таблицы, с обязательными ссылками на gid. Кандидатов (общих получателей/плательщиков до 2 колен) находит код; LLM — OpenAI (`gpt-5-mini`, Chat Completions) — только формулирует ответ. Ключ из `OPENAI_API_KEY` или `openai_key.txt`. Fallback без ключа, без сети или при ошибке API: шаблонный ответ по тем же фактам.

## 4. Надёжность и производительность

- Объём: 2 248 узлов — все алгоритмы networkx укладываются в секунды; `betweenness` полный (не sampled). `simple_cycles(length_bound=5)` — сотни циклов, доли секунды.
- Детерминизм: `seed=42` в Louvain; сортировка `top_nodes` по `(−priority, gid)`; float округляем до 6 знаков в CSV.
- Валидация на выходе (`export.py`): 2 248 строк, `role ∈ ROLES`, `evidence` непустой и ≤ 200, `cluster_id ≥ 0`, `top_nodes ≥ 20` — падаем с понятной ошибкой, а не пишем битый файл.
- Ошибки данных: узлы без рёбер → все метрики 0/NaN, роль peripheral, evidence обязателен.
- Зависимости минимальные: pandas, pyarrow, networkx, numpy, streamlit, pyvis. Всё pinned в `requirements.txt`; проверка на чистом venv — обязательный шаг перед сдачей.

## 5. Компромиссы и альтернативы

| Решение | Альтернатива | Почему так |
|---|---|---|
| Правила с порогами | кластеризация признаков / ML-классификатор | must-have 3 требует объяснимость; ground truth нет — accuracy не измерить |
| Louvain на ненаправленном графе | Infomap / directed community detection | из коробки в networkx, детерминирован seed'ом; направление уже учтено в ролях |
| Пороги по квантилям разведки, зафиксированы в config | адаптивные пороги | адаптивные сложнее объяснить жюри; в README указываем, что при росте графа пересматриваются |
| Streamlit + pyvis | отдельный фронт / Jupyter | 1 час на рабочий экран; ноутбук хуже для «найдите gid при жюри» |
| LLM только в объяснениях/гипотезах | LLM в присвоении ролей | «чёрный ящик» не засчитывается; LLM недетерминирован |
| truncated → peripheral + скор похожести | truncated → terminal | ТЗ явно называет это ловушкой; скор — честный компромисс |

## 6. Масштабирование до ~1 млн узлов (раздел для README)

- networkx → igraph/graph-tool (или cuGraph на GPU); pandas → polars/DuckDB для агрегаций.
- Betweenness — только approximate (k-sampling) или на подграфе ядра; PageRank/Louvain масштабируются.
- Расчёт по компонентам параллельно; хранение features в Parquet/ClickHouse, UI читает срез вокруг gid, а не всё.
- Пороги ролей — по квантилям на всём графе, пересчитываются при загрузке; правила не меняются.
- Инкрементальность: новая выгрузка — пересчёт только затронутых компонент.
